# Отчёт по безопасности и рефакторингу проекта «uchet»

Дата: 2026-09-20 | Ветка: `refactor/security-and-structure` | Только локальные коммиты, push не выполнялся.

## 1. Что за проект

Next.js 16 (App Router, Turbopack) + React 19 + TypeScript. Финансовый учёт по дням с магазинами
(workspaces) и разделяемым доступом.

- Аутентификация: NextAuth v5 beta (Credentials + JWT/JWE alg=dir enc=A256CBC-HS512), bcryptjs.
- БД: PostgreSQL 17, TypeORM (EntitySchema, synchronize:false, migrationsRun:false), параметризованные запросы.
- Тесты: Vitest 5, @testing-library/react, Playwright (chromium).

Границы: весь аудит и прогон - строго локально: `next dev` на 127.0.0.1:3001 ->
Docker-Postgres `uchet-local-db` на 127.0.0.1:55432. Прод (Neon) не трогался, наружу ничего не уходило.

## 2. Поверхность атаки

Логин/регистрация, сессии и отзыв токенов, IDOR и изоляция аккаунтов, приглашения и согласие,
привилегии (owner/editor), парсинг id/даты/текста, инъекции, тайминг-оракул, CSRF/open-redirect, CORS,
заголовки и cookie, PWA-cache, раскрытие исходников, HTTP-эзотерика (smuggling/XXE/chunked/Range/Expect),
гонки, миграции.

## 3. Найденные и исправленные уязвимости

| # | Проблема | Серьёзность | Исправление |
|---|---|---|---|
| 1 | Утечка списка email (перебор существования аккаунта) | High | Закрыт канал availableUsers; логин/регистрация не раскрывают существование |
| 2 | Тайминг-оракул входа (157 мс vs 84 мс) | High | Дамми-bcrypt для неизвестного пользователя, константное время (~0 мс) |
| 3 | int4-переполнение workspaceId=999999999... -> 500 | Medium | parsePositiveInt с границей int4 -> 404/400 |
| 4 | NUL-байт в тексте -> 500 (сбой Postgres) | Medium | sanitizeText вырезает NUL (U+0000) |
| 5 | accept/decline отдавали 200 для чужого/несуществующего/повторного | High | SELECT-pending -> UPDATE/DELETE с проверкой affected/row; 404 |
| 6 | Доступ к магазину без явного согласия | Critical | Членство pending; доступ только после accept; подмена status/role игнорируется |
| 7 | Токен продолжал работать после logout | High | users.session_version + bump в events.signOut -> старый токен 401 |
| 8 | Дубли автозаписи операции (2 POST на строку) | Medium | Побочный эффект вынесен из setState-апдейтера (StrictMode) |
| 9 | Нет COOP/CORP/X-Permitted-Cross-Domain-Policies | Low | Добавлены; в проде + HSTS и CSP |
| 10 | Отсутствовал NEXTAUTH_SECRET / пустые .env | High | Добавлен dev-secret, удалены пустые .env/.env.local |

## 5. Главный инвариант - изоляция двух тенантов (новый блок)

Кластер ABC (магазины A1..A4, люди a1..a4) и DEF (B1..B4, b1..b4) с одинаковыми именами магазинов
и уникальными секретными маркерами. Доказано на двух уровнях:

- tests/security/tenant-isolation.test.ts (Vitest, 7 тестов): полная матрица каждый пользователь x каждый
  чужой shop id по GET/POST/PUT/DELETE -> 404; скан на утечку чужих маркеров; кросс-приглашение с
  обязательным согласием; обход согласия (подделка статуса/роли/владельца, self-add, replay/decline);
  remove -> мгновенный 404 -> re-add снова pending; равенство таблицы членств ожидаемому набору (БД-оракул).
- pentest/22-two-tenant-matrix.sh (живой сервер + реальный логин, 29 проверок): та же матрица через HTTP,
  плюс владелец A никогда не видит B даже после кросс-согласия.

Дополнительно (второй заход, фокус на таблицу календаря):

- tests/security/operation-idor.test.ts (Vitest, 3 теста) - матрица по id операции: для каждого
  пользователя x каждой чужой операции x каждого магазина PUT/DELETE -> 404, плюс скан на утечку
  чужого маркера и проверка целостности (чужие строки не изменились). PUT/DELETE в коде дважды скоупят
  WHERE id = :id AND workspace_id = :workspaceId, поэтому подставленный чужой id не срабатывает.
- tests/e2e/table-leak.spec.ts (2 теста) - UI-проверка самой таблицы календаря: A заводит секретную
  строку, B (другой аккаунт) открывает тот же день - в DOM и в ответах /api/financial-data секрет
  отсутствует; при шаринге B видит ровно строки общего магазина и никогда строки другого магазина A.
- pentest/23-operation-idor.sh (живой сервер, 2 проверки) - та же id-матрица по HTTP.

Итог: пересечь кластеры нельзя ни добавлением, ни передобавлением, ни подбором id, ни подделкой тела,
ни чужой сессией. Доступ только явным приглашением владельца + согласием, и только к одному магазину.
Зафиксировано коммитом 75f6b00 (2 файла, +303 строки).

## 6. Задокументированные не-проблемы (осознанные trade-off)

- TRACE -> 500: ограничение Next.js 16 (middleware не перехватывает); не эксплуатируется.
- Rate-limit доверяет X-Forwarded-For: на Vercel выставляется прокси.
- Регистрация существующего email -> 409: осознанный UX-выбор.
- CSP содержит unsafe-inline: для ужесточения нужен nonce/hash.
- Таблица user_sessions не используется (сессии в JWT).

## 7. Что ещё могли упустить / что осталось (по приоритету)

1. Секреты в git-истории: прод-DB пароль (npg_...) и NEXTAUTH_SECRET лежат в публичных коммитах

3. Проверка Origin для state-changing API: сейчас держится на SameSite=Lax cookie. Добавить явный Origin/Referer.
4. Восстановление доступа / верификация email отсутствуют (нет forgot-password, 2FA, проверки почты, HIBP).
5. Аудит зависимостей: yarn npm audit / Snyk / Dependabot не прогонялись.
6. Браузерный двухаккаунтный E2E: есть sharing.spec и pwa-cache, но нет выделенного два контекста A+B одновременно.

### Желательно
